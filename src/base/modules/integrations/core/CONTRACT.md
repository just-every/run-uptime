# Integrations core public contract (v2)

Source exports are `core/index.ts`. Types live in `core/types.ts`. No dependencies are required; Node SQLite and Node HTTPS adapters are separate imports (`core/sqlite.ts`, `core/node-transport.ts`) from the portable D1/core code.

Provider units implement `DeliveryProtocol` with `id`, async `prepare(envelope, nowMilliseconds)` returning `{url, headers, body}`, and synchronous `classify({status, headers, body}, now)` returning an `Outcome`. `prepare` reads trusted credential/destination configuration using `envelope.destinationId`; never accept arbitrary bot URLs or caller credentials. URL must be stable for a destination version. Core hashes the prepared URL at enqueue and rejects configuration drift at dispatch. `body` must exactly equal the immutable envelope body. Prepare must perform no HTTP requests. Providers expose their own serialization and configuration factory; pass the resulting protocol to core. Classifier returns accepted/rejected/retryable/uncertain, fixed safe `code`, optional status and retryAfterMs. Never include raw provider text, URLs, auth, or personal data in codes. HTTP errors without proven rejection are uncertain. All lost responses and classifier errors become uncertain. Non-idempotent providers never automatically replay uncertain attempts.

`new DeliveryService({repository, protocols, transport, now?, hashDestination?})`; `enqueue(envelope, {maxAttempts?, retryDelaysMs?}?)`; `dispatch(id)`; `dispatchDue(limit=100)`; `recoverExpired()`; `get(id)`; `log(id)`; `resolveUncertain(id, 'accepted'|'rejected', evidenceCode)`. Calls are tenant-scoped by the repository. Logical ID, tenant, destination ID, protocol, event and exact body are immutable. Reused IDs with changed content reject. Default maximum 4 attempts, delays 1s/5s/30s; explicit retryable outcomes are bounded. Accepted means protocol acknowledgement, not confirmed human receipt. Expired claims remain uncertain with durable history. Reconciliation is a trusted operator call; no general replay switch exists.

`hashDestination?: (url: string) => Promise<string>` is a trusted consumer callback, called with the exact prepared URL after URL/body validation at both enqueue and dispatch. It must return 64 lowercase hexadecimal characters, optionally prefixed by a 1–16 character version identifier (lowercase ASCII letter first, then lowercase letters, digits or hyphens) and `:`; for example `hmac-v1:<64 lowercase hex characters>`. Other output rejects before insertion or transport; dispatch records only `rejected` with code `preflight_failed`. Without this option, the SHA-256 URL digest and all default delivery/request fields are unchanged. The resulting string participates in the existing immutable fingerprint and destination comparison. Hashing does not change the wire request, retry policy, claim check or uncertain-send semantics.

Consumers needing protection against offline URL guessing can capture a separately configured 32+ random-byte HMAC key in this callback and return a versioned HMAC-SHA256 digest. One consumer format is `hmac-v1:` plus lowercase HMAC-SHA256 of the UTF-8 lowercase SHA-256 hex digest of the prepared URL; it also permits consumer-owned rekeying of existing URL digests without recovering plaintext. Base performs no URL normalization in the callback path. The consumer owns canonical URL preparation, stable algorithm/key custody across enqueue and dispatch, immutable destination versions, and any coordinated migration of existing hashes and fingerprints. Changing the algorithm/key without that migration rejects existing work. Keep the key outside delivery storage and transport requests. Default SHA-256 is unkeyed, and this option does not encrypt destinations or automatically protect consumers that do not adopt it.

`new IntegrationsRepository(sql, namespace)` uses an actual transactional SQLite/D1 database. `D1SqlDatabase(binding)` adapts D1; `SqliteDatabase(path)` adapts Node built-in SQLite. Apply `core/schema.sql` once in the consumer migration chain; numbering is the integrator's. Namespace must be server-selected per installation/tenant; envelope tenant must equal namespace. Never expose repository or service management calls directly to unauthenticated input.

`createWebhookProtocol({resolveDestination, signingKey, timestampedBodySignature?})` accepts a trusted `(destinationId)=>Promise<string>` and async `signingKey(envelope)=>Promise<Uint8Array>`. 32+ random-byte HMAC keys, held outside delivery storage. Signatures bind version, tenant, destination ID, event, logical ID, timestamp and exact UTF-8 body. Receiver uses `verifyWebhook({body,headers,key,tenant,destinationId,now?,toleranceMs?})`, then `repository.acceptReplay(verified)` BEFORE applying its effect. Replay claims are permanent; duplicate effect must not be reapplied. For transactional effect processing consume the durable replay inbox, with the edition's effect in the same DB transaction; external effect uncertainty still needs reconciliation. Receiver signature success alone is not replay protection.

`timestampedBodySignature: {timestampHeader: string, signatureHeader: string, signingKey?: (envelope: Envelope) => Promise<Uint8Array>}` is an optional generic compatibility format, also exported as the `TimestampedBodySignature` type. It adds an ISO 8601 UTC timestamp (`new Date(timestampSeconds * 1000).toISOString()`, with `.000Z`) and unprefixed, unpadded base64url HMAC-SHA256 over UTF-8 `isoTimestamp + '.' + exactBodyString`. Both timestamps represent the same whole-second instant. Exact Unicode, whitespace, newlines and BOM are preserved. Header names must be HTTP token names, unique ignoring case, and must not collide ignoring case with `content-type`, `webhook-id`, `webhook-tenant`, `webhook-destination`, `webhook-event`, `webhook-timestamp` or `webhook-signature`. Configuration is validated and captured at creation; no metadata override is provided. The optional key callback resolves a separate key; otherwise the already-resolved Base key is reused. Both keys must be `Uint8Array` values of at least 32 bytes. A consumer whose established contract signs with a random secret string may explicitly encode its literal UTF-8 bytes for either key instead of decoding it as hex/base64. Keys and configured values never enter delivery rows or logs.

Without this option the request is byte-identical to the default Base format. With it the Base signature and headers remain intact, and `verifyWebhook` continues to verify only the Base format. The additional signature does not bind Base metadata; its receiver owns freshness and replay/effect handling. It changes no classifier, uncertain-send, retry, transport or security semantics.

The compatibility header names also cannot replace transport-controlled or authorization headers: `host`, `connection`, `content-length`, `transfer-encoding`, `proxy-authorization`, `authorization`, `keep-alive`, `proxy-connection`, `te`, `trailer` and `upgrade`. These reject at protocol creation even when using a Worker transport.

`new TokenService(repository, authority, now?)`: `issue(context,{name,scopes,expiresAt?})`, `authorize(token,requiredScopes,{requestId,resource})` (durably records every allowed/denied attempt and returns safe metadata or null), `revoke(context,id)`, `list(context)`, `usage(context)`. TokenAuthority's trusted async grant callback returns `{scopes, commitGuard: {sql, params}}`, and administer rejects unauthorized administration. `commitGuard.sql` is a trusted SELECT that returns a row only if the authenticated issuer is still active/authorized and every durable revision used to derive `scopes` is unchanged. Core embeds it as an EXISTS predicate inside the token INSERT in the same SQLite/D1 batch as the issuance audit. A stale/missing issuer or grant revision rejects issuance, returns no token and creates no issued audit event. An audit failure rolls back issuance. A plain scope array or missing guard rejects; there is no compatibility fallback. The consumer must store authority in the repository database and update its revision(s) in every transaction changing issuer permissions or grant ceilings, including removal and reactivation. A query checking a constant/preflight value or a different database does not implement this contract. Every use checks current scopes, expiry/revocation in SQL and records usage atomically. Plaintext is returned only by issue, database persists SHA-256 hash only.

Transport is required and trusted: `TrustedTransport.send` MUST enforce public IP validation at connect time, verified TLS, no redirects and bounded response/request time. `NodePinnedTransport` is the supplied production enforcing implementation. Worker consumers must supply a trusted pinned-resolution egress service/runtime port; plain fetch is explicitly unsupported. Only tests may provide a transport mapping synthetic HTTPS URLs to a real loopback receiver. There is no production test flag.

`isPublicAddress` uses the single maintained range policy in [public-address.ts](public-address.ts), shared by `validateDestination` for literal URLs and `NodePinnedTransport` for **every** DNS answer before connecting. Mixed public/non-public answers reject as a whole. The conservative policy excludes private, loopback, link-local, multicast, reserved, documentation, benchmarking and special-purpose allocations, even when a special-purpose address is globally reachable. This includes Azure `168.63.129.16`, IPv4 <code>192.31.196.0/24</code>, <code>192.52.193.0/24</code>, <code>192.175.48.0/24</code>, IPv6 `2620:4f:8000::/48`, `3ffe::/16`, and both ISATAP interface-identifier forms. IPv6 must be ordinary `2000::/3` unicast outside the exclusions; mapped/translation/transition forms reject. Base retains its broader <code>192.0.0.0/16</code> and `3fff::/16` exclusions. Compressed and expanded IPv6 follow the same policy. The direct IPv4 guard requires four canonical decimal octets (0–255), with no leading zeros except a single `0`. URL parsing normalizes IP aliases before literal validation; malformed addresses reject. The portable guard imports no Node APIs.

## Adoption details

`dispatchDue` discovers due jobs from durable storage after restart; schedule it from a consumer queue/cron. Claims last 60 seconds, and the supplied transport bounds DNS to 15 seconds and a connection/request to a further 15 seconds by default. User-supplied prepare callbacks should also finish within the claim horizon. Core checks the durable claim and its expiry again after preparation; an expired or reconciled claim cannot start a late request. An expired in-flight attempt is never overwritten by a late response. Any database exception propagates to the caller; the application must expose that failure. No send occurs without a committed attempt row. A retryable final attempt has state `rejected` and retains its explicit retryable provider reason in the attempt log.

Signature canonical input is the UTF-8 encoding of JSON.stringify(["integrations.webhook.v1", tenant, destinationId, event, id, timestampSeconds, exactBodyString]). Outbound bodies must round-trip through UTF-8 without replacement. The header set is `webhook-id`, `webhook-tenant`, `webhook-destination`, `webhook-event`, `webhook-timestamp`, `webhook-signature` (`v1=` plus lower-case SHA-256 hex). A request is fresh within 300 seconds by default (configurable downward only). The key is raw random bytes, not a password or hex string; decode a configured hex/base64 secret to bytes before calling. This version has one active verification key; coordinated key rotation is consumer-owned and no implicit multi-key behavior is claimed.

Receiver `body` is the original `Uint8Array`, obtained from `new Uint8Array(await request.arrayBuffer())` in Fetch/Workers or concatenated raw Node request chunks. Verification decodes strict UTF-8 with `{fatal: true, ignoreBOM: true}`: malformed encodings reject, and a leading UTF-8 BOM remains part of the signed text. No Unicode normalization or JSON parsing occurs. The existing string input is only for caller-owned canonical text and rejects unpaired surrogates; it cannot prove bytes already lost by `Request.text()`, `Buffer.toString('utf8')`, a default TextDecoder, or middleware. Those are unsupported receiver boundaries. Pass only the returned `verified.envelope.body` to subsequent parsing and inbox processing. See the [native receiver guide](../receiver.md).

Receiver replay rows are a durable inbox, not proof an external side effect completed. `acceptReplay` returns true exactly once for a logical ID and rejects changed signed contents, even after restart. Do not erase replay rows while the logical ID can be reused. For transactional business effects, adopt `integration_replays` as an inbox and maintain the application's processed marker in the same database transaction as that effect; do not blindly execute an effect again after a receiver crash. Response-lost external effects require reconciliation just like outbound delivery. There is deliberately no automatic uncertain-send retry, even for custom webhooks.

Secrets never enter delivery rows: URL hashes bind the trusted destination version, while full secret URLs, bearer headers and signing keys are resolved only for the current attempt. Payloads are durable product data and must not contain credentials. Logs retain machine codes, status, timestamps, feature/protocol identity through the envelope, and reconciliation records. They do not retain provider bodies/error messages. Consumer credentials, destination lookup, authorization contexts, scheduling, egress declarations and UI/operator audit actors remain consumer wiring. Do not treat any caller-controlled `Context` or destination registration as trusted without native server authorization.

Retry policy (maximum attempts and delay vector) also participates in immutable enqueue identity. Attempts are capped at ten and each configured delay at one day. A retry-after delay above one day terminates as `rejected` with code `retry_delay_exceeded` rather than retrying earlier than the destination requested. There is no total elapsed retry horizon; multiple delays and late dispatch can extend beyond one day. Issuance/revocation and their feature-tagged audit events commit together; token event rows survive token deletion. Integrating editions may supplement these with native human actor audit identity.


## Token API v2 adoption

`DeliveryProtocol`, signing, delivery and transport signatures are unchanged. Token grants require a commit guard and token authorization requires concrete request context. For example, a trusted consumer reading its own `issuers(namespace,id,revision,active,scopes)` record can return the parsed scopes plus `commitGuard: { sql: 'SELECT 1 FROM issuers WHERE namespace=? AND id=? AND revision=? AND active=1', params: [namespace, authenticatedIssuerId, readRevision] }`. Revisions must never be reused across removal/recreation. If scope ceilings depend on multiple rows (roles, application approvals, session state), the guard must bind/check all of them. The SQL is supplied only by trusted server policy, never by request input. It is a SELECT without a trailing semicolon; it may join native consumer tables and uses positional `?` parameters. Parameter arrays and scopes are copied before asynchronous hashing. Core owns no issuer registry or identity policy.

Each `authorize` call must supply `{requestId, resource}` from the handling application's request/resource identifiers, including denied or unknown-token attempts. Both fields use the existing safe identifier grammar: 1–200 ASCII characters, first alphanumeric, then alphanumeric or `_.:/-`. They must not contain credentials or raw URL/query/body data. Missing/invalid context rejects before authorization and does not invent a usage receipt. The recorded fields bind the decision to the supplied request and resource; this does not make resource-level access decisions on behalf of the consumer. Required scopes remain consumer-selected, and repeated request IDs produce separate attempt receipts. Request context is copied before asynchronous work. Both allowed and denied valid calls commit their context together with the live token decision. Usage storage failure rejects visibly.

`schema.sql` remains an unnumbered fresh-install proposal. Consumers that already applied the earlier proposal must separately apply `upgrade-token-usage-context.sql` exactly once in their migration chain (numbered by their integrator); rerunning CREATE TABLE IF NOT EXISTS is not an upgrade. That expansion preserves historical usage with null request/resource rather than inventing provenance. New service calls always write both validated fields. Audit and usage survive credential deletion.
