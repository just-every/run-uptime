# Uptime safety rules and implementation detail

This page keeps the mechanism, retained safety rules and current implementation detail that CONTRACT.md held before the 28 October 2026 contract cleanup, moved here word for word. CONTRACT.md is the only source of acceptance text and status; where this page and a clause differ, the clause wins. Its sections are linked from the clauses that rely on them.

## Retained safety rules and current implementation detail

These rules retain the existing security, evidence, erasure and Base replacement policies. Limits described as current implementation are evidence of distance to the target clauses above, not exclusions from that target. New private grants, script execution and browser artifacts require their named acceptance journeys before support is claimed.

## Declared external data flows and baseline replacements

`seed.json → externals` declares the source-level outbound data categories. Public HTTP(S) monitors and status-only canaries resolve each public target, validate every redirect hop, and send the configured method, path/query, allowed headers and request body to the target. A request credential is sent only to its exact owner-authorized monitor origin; cross-origin redirects strip it, custom headers and body. Ordinary checks read bounded response status, headers and body for assertions without retaining raw bodies in observations; EVIDENCE-002 stores a separately retained, redacted failure excerpt with bounded request/response and timing facts. Its opt-in isolated browser renders that received excerpt as an encrypted PNG without another target request; scripts, styling, media and network are blocked. Snapshot access, retention, archive portability and erasure follow EVIDENCE-002. A canary is a status-only `GET` with no credential, custom headers or body and reads zero response-body bytes. DNS queries reveal only the hostnames being resolved plus source network address and lookup timing to the resolver configured for the runner.

TCP and TLS monitors connect to the owner's public host and port at its validated address: TCP sends nothing and may read up to 512 bytes of banner (256 printable characters kept); TLS sends a ClientHello naming the host and keeps certificate subject, issuer, names, validity and fingerprint. DNS monitors send the monitored name and type to the selected public resolvers (Cloudflare, Google) over HTTPS and, when chosen, one non-recursive query over TCP to the zone's authoritative server; bounded normalized records are kept. Domain monitors send the domain name to IANA's RDAP bootstrap, its registry and the registrar record the registry links, over HTTPS; the expiry date, source and update time, status values and redaction or conflict are kept. These flows are declared in `seed.json` as `public-protocol-targets`, `dns-over-https-resolvers` and `rdap-registries`.

Discovery is read-only and runs on the owner's runner; a hosted demo, which has no runner, runs the same crawl and limits in the Worker over public GET/HEAD requests without credentials. It may follow any validated public redirect from the initial URL; subsequent crawls are bounded to the final/input registrable domains and linked status hosts, subject to robots and request/time/body limits. It may request robots files, permitted pages, JSON/spec documents, conventional API hosts and status hosts. Bounded response content is parsed in runner memory. Only validated definitions, hostnames, URLs, short notes and request/timing summaries return to the Worker; raw HTML, response headers and page bodies do not. The Worker stores only the bounded derived result. No supplied HTML is rendered as console HTML.

An owner-authorized discovery source (DISCOVERY-001) is read only when the owner runs it, and only by the owner's runner. A domain source sends DNS queries for the domain's usual host names to the runner's resolver, then GET or HEAD requests to the hosts that resolve to public addresses. A robots/sitemap or OpenAPI source reads those public files and requests the routes they list. All of these requests follow the discovery fetcher's robots, budget and public-address rules. A provider source sends the provider only its account identifiers (a zone ID, repository, project, site, or application and deployment group) and documented read-only list requests. Each request carries a runner-local read-only credential that the Worker never receives, stores, exports or logs:

- Cloudflare: zone details and DNS records.
- Route 53: GetHostedZone and ListResourceRecordSets, signed with Signature Version 4.
- GitHub: deployments, their statuses and workflow runs.
- Vercel: deployments and project domains.
- Netlify: the site and its deploys.
- CodeDeploy: ListDeployments and BatchGetDeployments, signed with Signature Version 4.

The runner refuses any other method, path or operation before it is sent. Only derived candidates with their provenance (source, identifier and time seen), short notes and validated proposed definitions return to the Worker. These flows are declared in `seed.json` as `discovery-cloudflare-dns`, `discovery-route53`, `discovery-github-deployments`, `discovery-vercel-deployments`, `discovery-netlify-deploys` and `discovery-codedeploy`. The DNS and site requests extend `site-discovery`. DEPENDENCY-002's live check of a catalog status source is `service-catalog-status-sources`: one read-only GET per address the catalog itself names.

Browser flows send ordinary browser requests to owner-declared top-level origins and any public subresource or WebSocket host reached by a page; redirects and subresources pass the same destination-filtering proxy, which blocks private, loopback, link-local and metadata addresses. The destinations receive request paths, browser headers, source address and timing, and cookies that a destination itself sets. A named runner-local credential can be filled into a form only while the page is at its exact configured origin, so that destination may receive that value as part of its form request. The isolated runner browser processes page content locally; only the sanitized step trace returns through the control plane, not screenshots or page bodies.

The private runner sends signed enrollment, capabilities, claims, contact timing, signed attempt evidence and derived discovery results to the owner-configured control-plane origin. It receives assigned monitor/flow definitions and discovery jobs from that control plane. A notification claim can return the selected endpoint URL, signing credential and event content to the runner, which sends the one authorized webhook or Slack request and returns its bounded delivery outcome. The hosted Worker submits queued email through the selected Base mail adapter and sends webhooks and Slack itself. Owner-console requests prompt due checks and sends; Cron continues background work after activation. A private runner may also claim delivery work, but never receives mail-provider credentials. The selected mail provider receives its API-key authorization (and Cloudflare account identity when selected), sender and recipient addresses, message subject and text/HTML body, sign-in links, incident/test/watch content and drill confirmation links. SendGrid receives the delivery ID in custom arguments, and Resend receives it as the idempotency header. Provider acknowledgment does not establish recipient acceptance. Optional runner-local watch endpoints receive only unreachable/recovery state and timestamps. An optional owner-configured heartbeat URL receives an empty HTTPS request whose capability path, source address and timing are visible to that service. The shared local lifecycle also makes a readiness `GET` to the selected application origin (normally local loopback, possibly an owner-selected remote origin); the CLI follows HTTP redirects, sends no configured authorization header or body, and reads the health status/JSON value.

The optional `IDENTITY_PROVIDER` setup declaration is not a working sign-in feature. The completed local probe passes the real public contract check, omitted-provider setup, native email-link sign-in and `/setup` handoff, native session revocation, and repeat setup with exact settings, owner and dependency-row preservation. With a selected provider, the real CLI reads dependency metadata from a local issuer edge, then setup fails at the unmounted application dependency-approval route (404) before creating an owner; no provider link request is made. A separate native bootstrap succeeds, but dependency discovery/linking and OIDC start/callback routes remain 404 with no durable link or identity records. That 404 is not linked-provider revocation proof. The current Worker does not exchange authorization codes, user tokens or JWKS. The default is a separate scoped provider-lifecycle adoption round; this proof establishes no linked-provider readiness. Likewise, the private management editor is an explicit owner-configured integration: when the exact management origin and installation identity are supplied, an authenticated owner page creates its iframe while hidden and sends installation, parent-origin and surface context, followed by the page path after handshake. Visible page text and element descriptors are sent only after the owner opens the editor and enables context sharing. Uptime provides no public embeddable widget.

For **BASE-INPUT-002**, Uptime replaces arbitrary-HTML sanitization with no owner-supplied HTML field and derived-only parsing of fetched public target content. For **BASE-INPUT-003**, Uptime has no R2 binding or product attachment-upload route; bounded definitions and archives are structured data, not attachments. For **BASE-PUBLIC-002**, Uptime has no public embeddable surface; only the separately configured private management editor origin is used. For **BASE-DATA-005**, the replacement is a standalone native product with no operational dependency on the marketplace or author, plus an optional owner-configured private management editor. That opted-in editor may contact the author when the configured management origin belongs to the author; an absolute author-zero-egress claim therefore does not apply to that configuration. The native product must remain usable without it. No telemetry, license check or kill switch is authorized by this exception. These are explicit scope replacements, not untested baseline passes. A measured emitted-runtime probe with optional integrations absent denied outside Worker/browser traffic and the exercised runner HTTP(S) transport and passed native sign-in, actual local-edge monitoring failure/recovery, history and export, with zero outside browser requests at 1440/390. Hostile text in monitors, destinations and structured definition imports stayed literal without planted requests or script execution; unknown uploads were refused without durable effects. This proves the tested native flows operate independently. The source inventory and scoped trace do not establish complete optional-provider or hosted/deployment egress.

## Stored evidence and independent failure agreement (C3)

A slot outcome and scheduled confirmation/recovery streaks are pure projections of stored attempts, recalculated on each arrival in chronological slot order. A derived checkpoint folds only expired acceptance windows and keeps exact, unclamped counters; complete slots still accepting late attempts remain mutable. Reads re-evaluate current freshness without advancing the checkpoint counters. Failing requires terminal target failures from two distinct runner network labels, or one failing vantage with its passing canary in the same slot. A failed canary counts its network absent; its failure remains Degraded. Missing/expired evidence is Unknown; recovery requires complete fresh passing coverage. Same-label runners count once. New enabled production monitor settings refuse configurations incapable of reaching Failing: a public monitor on one network label with no external check URL of its own takes the installation's External check URL (an owner-only setting on Runner / archive, seeded with `https://example.org/`) into its saved revision, so it is refused only when the setting is absent. An external check on the monitored site itself (the same hostname, ignoring case and a leading `www.`) is refused whether it is the default or the owner's own, because it would fail whenever the monitor does and a failure could never be confirmed. Revisions are immutable, so changing the setting applies to monitors saved afterwards and never rewrites a saved one. The setting is installation-local and does not travel in archives; the URL a revision carries does. Assignment-free historical revisions keep their saved terminal-probe failure quorum until the owner saves a new revision; the overview and count-only owner notices flag the need for a second independent network or an external check URL. `tests/resilience/attempts.mjs` proves these flows through signed Worker routes and real probes at local network edges.

## Per-runner assigned attempts (C4)

Each runner has an independently revocable key and a declared network label. A revision assigns each probe to a runner. The immutable attempt identity is slot/probe/attempt number; only that assigned, unrevoked runner can submit it inside the acceptance window. The first accepted copy wins. Results have no slot-wide lease owner and may contain any assigned subset. Stored evidence, recalculated state and incident events commit atomically under a generation guard. Migration preserves the existing runner as the first row. C5's pinned resolution remains unchanged. `tests/resilience/attempts.mjs` covers migration, signatures, assignments, duplicates, expiry, order and revocation through public routes.


## Evidence and state

Every scheduled slot and attempt retains its monitor revision, policy, selected probes, runner version, start/completion, status, assertion results and error category. Retries are attempts inside a slot and never erase an earlier failure or increment scheduled confirmation/recovery streaks. Raw target response bodies and probe-request secrets are not retained in observations (EVIDENCE-002's redacted failure snapshot is stored apart from them); notification destination credentials remain installation-local and are omitted from portable archives.

The 24-hour and 7-day history coverage includes complete scheduled results across revisions, evaluated with each immutable revision’s settings and bounded by its next revision. Maintenance and paused periods are shown separately from observed and Unknown time; historical results cannot establish current-revision health. Last check retains the latest completed scheduled observation across revisions. REPORT-001’s per-monitor custom/24h/7d/30d/90d reports share immutable coverage, per-location latency, incidents/root causes, Unknown/paused/maintenance denominators and SLA figures across the console, CSV, JSON, owner-session API and authenticated paginated PDF. SLOW-001 event spans are clipped to the chosen period and overlapping spans merged into separate Slow time; they never enter downtime or SLA. Paged heartbeat run details retain revision, sequence, zone-aware times, outcome, duration, exit, late-run flag and redacted output. Scheduled recipient reports with durable delivery outcomes, service aggregation and labeled incumbent-history segments remain open.

Target evidence, coverage, and notification delivery are independent. Healthy requires fresh, complete selected-probe coverage and the configured recovery threshold. Incomplete passing coverage is Unknown. A fresh failure without independent-vantage agreement is Degraded; meeting the C3 agreement and confirmation threshold is Failing even when coverage is incomplete. Expired evidence becomes Unknown without silently resolving an open incident. Recovery requires complete fresh passing scheduled slots. Runner errors and absent observations remain distinct from target failure. Scheduled incident transitions and their destination jobs are committed with the corresponding observation and state change; a test send is separate from that history.

One-time and weekly maintenance windows use IANA time zones, explicit DST gap/first-repeat handling, previewed monitor selections and revision-guarded group apply/cancel with audit. Suppression preserves execution, observations and target state; an execution-pause window stops new checks while retaining in-flight evidence. Timeline and reports show maintenance separately with revision-bounded denominators. After a window expires or is canceled, actual completed evidence determines state and a real completed slot may open a still-confirmed failure. Recovery requires a previously open trigger, preventing orphan recoveries. Pending means stored locally. Manual checks do not change scheduled cadence, confirmation or recovery.

## Configuration diagnostics

The shared configuration table describes each binding, the runtime that consumes it, when it is required, and its validation rule. The Worker checks it before serving any path and before scheduled maintenance runs. Setup validates its generated or saved settings before starting its temporary runtime; the local app, preview, deployment and private runner validate their own configuration before serving or starting operational work. Invalid or missing values produce plain diagnostics naming the binding but never its value. The Worker's `/health` response is 503 until required configuration is valid. Hosted setup requires the selected Base mail provider credentials and sender address so email is not silently unavailable.

The applicable `/health` dependencies are D1 (including public admission, schema readiness and credential-custody storage) and the emitted `/app.js` through `ASSETS`; this product has no R2 or queue binding. One owner-authorized 3 s global response deadline (BASE-OPS-001 replacement, 2026-10-16) bounds configuration, public admission and those checks and returns 503 on unavailable dependencies. D1 has no cancellation API, so deadline expiry bounds the response rather than canceling the underlying operation. The historical 900 ms implementation’s retained local emitted-Worker health log records 15 total cases: healthy 200 and 14 dependency faults, all 503 within 906 ms, each followed by healthy recovery. Twenty sequential healthy samples have p95 6 ms and maximum 7 ms. These measurements establish neither hosted latency nor load capacity, runner operation, target health or provider acceptance. Existing public throttling still returns 429.

## Public paths and rate limits

`seed.json → deploy.publicPaths` declares sessionless documents, authentication routes, assets, health, credentialed runner and heartbeat APIs, owner-editor configuration, redirects and local-only development endpoints. The server still performs each route's normal authentication check after the rate-limit admission. `seed.json → limits.publicRequestsPerMinutePerIp` sets an owner-tunable maximum for each path class in a 60-second D1 window. Hosted requests use a keyed hash of the Cloudflare client-IP header; missing or malformed values share an unknown-client bucket. Local requests share a loopback bucket regardless of forwarded headers. Excess requests receive 429 and `Retry-After`; unavailable counter storage returns 503. Only expired public-rate counters are removed automatically; those counters are short-lived operational state and not product records. Limits are marked estimated and not load-tested, and do not establish capacity.

## Integrity and authority

Each Node runner signs purpose-separated enrollment and results with its own scoped key. Identity, declared network label, revocation and credentials stay installation-local. Legacy key-only clients resolve to the migrated first runner; they have no authority over other runners' probes. See C4 above.

Slot identity is monitor/revision/due time; attempt identity includes slot/probe/attempt. Manual requests have distinct identities. The acceptance window is bounded; expired, foreign or contradictory attempts are rejected and the first accepted copy wins. Edited or paused inflight work remains historical evidence and cannot change current state or events. Missed cadence is counted without fabricated catchup results. A scheduled check is due no sooner than one interval after the monitor's previous scheduled check was claimed and after its first attempt reported starting; after an edit, the shorter of the old and new intervals applies, so a late check moves later due times back rather than running checks closer together; equal runner and Worker clocks make the reported-start floor exact. Backward clock movement waits for due time; future evidence cannot establish health.

Observation, state and outbox writes share one durable transaction. Migration history is permanent. Completion verifies the immutable definition, fixed probe denominator, exact assertion bundle, outcome, clock bounds and transport limits. Live latency validation uses the larger retained elapsed measure. Historical archive compatibility does not relax live validation.

Every private document, mutation, observation read and export requires server-side operator or scoped runner authority. Missing configuration fails closed. Browser mutations bind the configured origin and reject cross-site requests. Loopback is not authentication. Shared Base operator-auth owns operator credentials and sessions; product policy must not silently grant additional roles. Signed reporting identifies the holder of the runner key; it does not prove an uncompromised runner.

## Network and credentials

Private-runner public HTTP(S) checks validate every A/AAAA answer and redirect hop, reject unsafe or mixed address sets, pin numeric sockets and retain original Host and SNI. Certificate verification is the default; NETWORK-002’s owner-saved fingerprint, private CA or acknowledged ignore exception applies only to the initial HTTPS origin, records bounded certificate/error facts and never authorizes credentials. Cross-origin redirects restore default verification. These exceptions require a private runner; the hosted Worker refuses them. Proxy environments are bypassed. HTTPS downgrade is rejected; an origin change strips credentials, custom headers, request body and mutating method. DNS, redirects, body and retries have bounded execution. Responses are limited to 64 KiB; compressed responses are rejected. An external check asserts status 200 only, so it stops at the response headers and neither reads nor keeps the body, however large the page; every other guarantee here applies to it unchanged. Independent network isolation remains an operating requirement. Hosted HTTP(S) and keyword monitors without runner-local credentials default to the Cloudflare Worker. Owner-console requests prompt due work; its one-minute Cron schedule continues background work, but initial Cloudflare activation can take up to about two hours. The Worker validates all public DNS answers and every redirect and uses Cloudflare’s public Internet fetch transport with certificate verification, no private-network binding, no cached probe response and the same time, body and assertion bounds. Numeric socket pinning is the private runner’s transport guarantee. The Worker is one network vantage; it uses the same configured canary and scheduled evidence rules and cannot supply independent regional agreement. TCP, DNS, TLS and domain checks also run in the Worker or an assigned private runner. Worker TCP cannot reach Cloudflare addresses, Worker TLS cannot inspect a TLS 1.3-only service, and a registry without RDAP has no WHOIS fallback; these cases remain Unknown as the protocol Status rows describe. Browser flows and checks using runner-local credentials require an assigned private runner.

Synthetic checks retain a separate live process/custody grant, exact path/port identity, expiry, GET/HEAD-only and no-redirect boundary. Grant authority is rechecked on every attempt.

Request headers/body, Basic, Digest and bearer authentication, OAuth 2.0 client-credentials or refresh-token acquisition, JWT signing and mTLS client certificates/keys use protected runner-local regular files with exact monitor-ID and origin binding, expiry and rotation checks. OAuth token requests use their configured HTTPS token endpoint; refresh state stays local. Credential failures remain distinct runner errors, and neither token material nor client private keys enter evidence or exports. Credential authority comes from the authenticated task envelope while its assigned probe and acceptance window are valid; another monitor on the same runner cannot use the same reference to obtain the credential. Setup runs numbered local-file migration 0001: valid unbound files used by exactly one existing monitor bind automatically, counting paused monitors; shared and unused files remain unbound with explicit owner instructions. Scheduled checks record bounded non-secret binding diagnostics and never bind files. Missing or invalid references yield runner errors without falling back to unauthenticated requests. Raw secrets and raw response bodies never enter observations, alerts or archives; only EVIDENCE-002's redacted excerpt may be stored, separately, and travel in archives. Portable historical references are not receiving-installation execution authority.

Heartbeat tokens are owner-issued, hashed at rest, scoped to an immutable revision and rotated on issuance. Server receipt time and strictly increasing sequences prevent replay in the current header form; HEARTBEAT-003's URL-capability form is labeled replay-unprotected. Ingress alone cannot change state. A scheduled slot freezes an installation-local receipt snapshot; signed completion must match it. Missing, stale, future, paused, revision-mismatched or imported receipts cannot establish Healthy.

## Flows

FLOW-004’s Chromium, Firefox and WebKit desktop/mobile execution and FLOW-003’s opt-in redacted failure artifacts are implemented. FLOW-001’s broader login/signup/checkout support qualification and FLOW-002’s reusable scripts retain their separate Status-table gaps. The following describes the constrained implementation and its retained safety obligations.

A flow is validated by the same function in the Worker, the definitions engine and the runner. Steps are `goto`, `click`, `fill` (a `credentialRef`, never a value), `waitFor` and `expect`; a target is exactly one of a plain CSS selector, text, label, or a role with its name. Required outcomes have an id and an expectation, and every one must be observed after the last step. Unknown step kinds and fields, scripts, other selector engines, secrets, intervals under 5 minutes, more than 20 steps or 8 outcomes, and more than 5 flows in an installation are refused with the entry named. Bounds per run: 60 seconds of wall time, 8 top-level pages, 5 MiB of response bytes, an 8 KiB trace; exceeding one fails the run and names it.

The runner serves a flow only through `runners/src/flow/`: its own process, a fresh 0700 profile deleted afterwards, an environment holding no inherited credential, proxy setting or Node hook, and the named credentials passed over a pipe. Chromium, Firefox and WebKit use the same authenticated filtering proxy inside the runner for pages, redirects, subresources and WebSockets. Engine-specific launch settings force proxy routing; page entry points for WebRTC and WebTransport are disabled before scripts run, service workers and downloads are blocked, and certificate verification remains enabled. The proxy resolves each destination itself and connects to the checked address. Public checks refuse private, loopback, link-local and metadata addresses; PRIVATE-001 grants authorize only their exact private targets, and the local fixture requires a synthetic grant. Each monitor fixes one browser and a desktop (1280 × 800) or mobile (390 × 844, touch, device scale 3) context. Firefox applies the mobile viewport/touch context without Playwright’s unsupported `isMobile` option. Signed evidence must match that immutable profile; independent network vantages evaluate the same profile, and reports and inactive archives retain it. A page may load top-level pages only on the origins the flow names and may not open a second window.

A flow runs a probe like any monitor, so incidents need the same vantage agreement. Failures keep distinct reasons (expected text or element missing, no element for a click, an error status, the wall limit, a forbidden address, a second origin, a missing outcome); a runner-side problem (no browser, a missing credential) is a runner error and the flow is Unknown. An observation's `flow.digest` must equal the digest of the flow in its slot's revision. Recovery compares the exact requirement set against the revision current when the open incident began: browser/device profile, required outcome ids with their expectations, and explicit `expect` steps. Removing or changing any original requirement, changing the browser/device profile, or switching monitor type makes a later pass a changed-definition recovery, labeled in state, recovery event and console with the revisions and removed requirements. Equal outcome counts cannot hide a changed expectation or profile; a pass in a new profile never proves the original profile recovered. Credentials are runner-local files bound to an exact origin and appear in no table, archive, export, log, trace or audit record. The flow tables are the existing monitor, revision, slot and observation tables; no table was added.

## Definition files and imports

One import pipeline, Base's import door, serves the owner's Definitions view and local command (`/api/operator/import/*`, origin-bound, owner session, the source named per request) and Business grants (`/api/rer/import/*`), with one server-side source allow-list; the read-only definitions export and recognition (`/api/definitions/recognise`) write nothing, and a plan's preview reads the door's retained plan. Importers only split a source into entries and map each to a file entry or an unsupported/refused reason; planning, apply and undo are source-independent. Definition batches applied before the door keep their read and undo routes. The UptimeRobot adapter maps HTTP(S), keyword presence/absence and heartbeat monitors, preserving exact expected status codes, classes and ranges (defaulting to 2xx/3xx), supported methods, a timeout bounded to 50 ms–10 seconds and intervals from 5 seconds to one day. Its saved heartbeat `interval`/`gracePeriod` mapping and the saved Better Stack heartbeat-page `period`/`grace` mapping create paused definitions with newly issued local URL authority; these bounded import paths do not establish live source-account cutover. Site24x7’s heartbeat threshold conversion remains part of the missing MIGRATE-004 implementation. Heartbeats require a new owner-issued token and list the old URL for repointing. Keyword case differences, timeout changes and unsupported monitor types are named. Request authentication, headers and bodies become a local credential reference without source secrets. An initial-origin ignore-SSL setting is preserved as an explicit private-runner exception. Source regions, assigned contacts, status pages, maintenance, tags/groups and expiry reminders are listed rather than silently discarded. Imported monitors use local-a and need a second network or a canary before enabling.

Saved Pingdom HTTP check-detail responses also map cadence, URL, literal criteria, local credential references and explicit certificate verification through reviewed paused apply. Separately, the saved UptimeRobot webhook-create-payload door preserves supported JSON/form/query templates, variable aliases and header names, discards source secrets and names unavailable variables; opaque integration detail and unsupported delivery modes refuse explicitly. ROUTING-002 separately previews saved UptimeRobot per-contact threshold/recurrence and Pingdom delay/repeat/recovery settings against an explicit local destination map, through the same reviewed route apply door. These bounded saved-file paths do not establish live extraction, all-contact/history migration, sibling handoff or authorized source-account cutover under MIGRATE-001/MIGRATE-002.

A recognized log export reports its row count and provenance; no row becomes a slot, observation, state or incident, so imported history cannot satisfy quorum, recovery or availability figures. Storing that history as labeled source history for reports, without it ever becoming evidence, is HISTORY-001’s target. Migration 0026 adds `definition_batches` and `definition_batch_entries`; monitor erasure removes a monitor’s batch entries and operator erasure anonymizes batch actors. `tests/definitions-import.mjs`, `tests/tls-trust-journey.mjs` and `tests/webhook-custom.mjs` exercise these saved-file owner doors with synthetic source inputs; `tests/archive-roundtrip.mjs` exercises inactive archive behavior. No real source-account migration or hosted import is established.

## Alert drills

A drill exists to check, one destination at a time, that an alert reaches somebody who can act. **Run alert drill** queues the test event with drill wording (`eventType` `uptime.notification.drill`, `kind` `test`, `incidentKey` null) for that destination's current credential. Disabled destinations can be drilled, as they can be tested. The one automatic attempt and the uncertain-never-resent rule are DELIVERY-001's. The message names who started the drill and when, and carries a link to `/alert-drill` holding a random 256-bit capability. Email has it as a text line and an HTML link, Slack as a message line, and the signed JSON webhook as an extra top-level `drill` object (`startedBy`, `startedAt`, `expiresAt`, `confirmUrl`) on drill events only. Incident events retain their immutable context; configurable webhook requests and payloads use WEBHOOK-001’s exact-byte signing. The default JSON envelope and Lamp-compatible signing remain available.

D1 stores the capability's SHA-256, bound to the drill, the destination and its credential. A copy sealed under the installation key lives only until the single send is over, and the runner reads it only while it holds that delivery's claim. The stored event, the stored webhook/Slack envelope, the archive and the console reads never contain the link. Opening the link (GET or HEAD) shows a page naming only the destination kind and the drill time. Only a same-origin form POST confirms, compared in constant time and accepted once within 24 hours. Unknown, used, expired and foreign links answer the ordinary 404 page, and the path is declared in `seed.json` under its own rate-limit class. The recipient needs no sign-in.

The console shows, per destination, "Last proven" (the latest confirmed drill for the current credential), "Not proven in 30 days" or "Never proven" in words, beside the latest drill's three lines:

- **Submitted** is when Uptime started the one send. Before then it says the drill is queued, or why nothing was sent.
- **Acknowledged** is when the provider or endpoint answered and with what code, or Uncertain or Failed with the code. Acknowledgment is not inbox receipt.
- **Recipient confirmed** shows the time someone used the link, reported by the recipient. Until then it is pending, and after 24 hours it reads "not confirmed within 24 hours" with nothing sent again.

Whether anyone acted is not measured. The first-run page lists any destinations already present with the same proof words. Drill history (`alert_drills`) is installation-local: archives carry the drill's delivery history like any test send, but never the drill rows, so restored destinations start Never proven. Erasing a destination erases its drills; erasing an operator removes the operator reference from the drills they started. Unmeasured: no hosted drill to a real inbox or channel has been run (see ACCEPTANCE.md).

## Portability and retention

Versioned archives include definitions, immutable observations, state, product outbox events, notification history for source records that remain, erasure receipts, the permanent anonymized action audit, source identity and erasure journal, and an integrity digest. Legacy development sign-in records are installation-local, not archive data, and remain until their associated operator is erased or local reset; no captured-mail viewer or new sign-in capture is exposed. Restore validates bounded UTF8 bytes, schema, version, semantics and hash before transaction and requires empty product data. Existing receiving-owner, runner-registration and idle-contact records do not make product data nonempty and remain unchanged by restore. Imported monitors gain new paused current revisions; leases are interrupted and alerts quarantined. Derived attempt checkpoints, request credential values, heartbeat authority, sessions, keys, grants, contact, webhook and Slack URLs, and signing keys are installation-local and are not imported; destination definitions and retained notification histories are portable. A local CLI receiving checkout must first run `rer setup --owner-email EMAIL --non-interactive` to establish its owner and settings; setup leaves product data empty for import. No imported event or receipt automatically replays. A digest checks changed bytes, not trustworthy provenance. To restore a pre-erasure archive after an erasure, export the later source journal from Runner / Archive and provide it to restore; local CLI import accepts its absolute path in `UPTIME_LATER_JOURNAL`. By itself, an old offline archive cannot reveal later erasure when restored into a fresh installation that has never received that journal. This is a limit of Base's offline transfer model.

Observation metadata, monitor definitions, destination and delivery history, audit history, and legacy development sign-in records have no automatic age/count deletion. The maintenance sweep deletes expired operator sessions, old owner/auth rate-limit windows, expired public rate-limit rows and old login-attempt counters. Short-lived authorization rows can also expire logically without being deleted; expired discovery jobs are marked expired and retained. Drill expiry/confirmation clears only the one-time capability ciphertext/hash while retaining the drill row. Owner rotation/deletion retires endpoint credentials by scrubbing their secret material after active sends finish while keeping the credential/history row. The notification bridge removes an `integration_attempts` row only when it proves that the exact attempt never reached the send boundary; its delivery reservation and job remain. ### Erasure and audit

Monitor erasure removes its revisions, slots, observations, derived attempt checkpoints, heartbeat claims and authority, incident events, related notification jobs and deliveries, and archive-history copies. Destination erasure removes the destination, all credential versions, dependent notification jobs, delivery attempts and outcomes, replay entries and matching archive-history copies. Operator erasure removes that operator's sessions, tokens, invitations, legacy development sign-in credentials and messages. For the original owner, the bootstrap claim keeps its singleton and claim time but replaces the operator reference with an unrelated anonymous UUID. Its receipt counts that row as anonymized, and the source journal fences its original primary key. The replacement commits in the same guarded batch as account deletion; setup remains claimed and receiving-installation authority remains local. The audit remains separate from the erased entity: its subject reference is opaque, and actor references for an erased operator become anonymized. Erasure writes a durable receipt with per-table counts and completion time in the same D1 batch as its audit record, deletion and Base portability erasure-fence statements.

The audit includes destructive actions and automated notification attempts, including test sends, plus operator authentication-mail provider attempts and legacy development capture history. The mail sender records the feature audit before attempting the provider request. Actor and subject fields are identifiers or feature names, never user-supplied names, emails, URLs or secrets. The audit travels in product archives. A later erasure journal makes restore refuse old audit actor references for an erased operator. Older offline archive bytes and external messages already sent cannot be changed by a later local erasure; a request already in progress may still reach its provider. Uptime does not use R2 or accept uploads, so there are no uploaded attachments to remove.
